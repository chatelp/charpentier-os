# Charpentier OS

Le système du ThinkPad X250, machine d'écriture dédiée : NixOS, une session sway sans décor où l'app Charpentier occupe tout l'écran, et la clé USB qui l'installe. C'est l'étape 5 du plan de l'app ([`charpentier-writer/docs/PLAN.md`](../charpentier-writer/docs/PLAN.md), phases 5.9 et 5.9 bis) ; l'installateur suit [`docs/DESIGN.md` §4.12](../charpentier-writer/docs/DESIGN.md) « Installation ».

L'app vit dans son propre dépôt, [`chatelp/charpentier`](https://github.com/chatelp/charpentier) (`charpentier-writer` en local), qui construit aussi son paquet Nix (`nix/charpentier.nix`). Ce dépôt-ci la prend comme entrée du flake, sur GitHub, figée à un commit par `flake.lock`.

## Construire

Sur une machine x86_64 sous Linux avec Nix (le Yoga L13 de Pierre, sous WSL2), `scripts/nix.sh` appelle Nix directement. Sur le Mac, qui n'a pas Nix, il le lance dans le conteneur officiel `nixos/nix` sous [OrbStack](https://orbstack.dev) (x86_64, par Rosetta : lent). Jamais sur le prodesk2021.

```bash
scripts/nix.sh build .#charpentier                        # le paquet de l'app
scripts/nix.sh build .#nixosConfigurations.x250.config.system.build.toplevel
scripts/nix.sh --out dist/installer build .#installer     # l'image de la clé
scripts/try-installer.sh                                  # l'essayer en machine virtuelle (Linux, KVM)
scripts/try-plymouth.sh start                             # l'écran du mot de passe du disque, dans une fenêtre (WSLg)
nix run .#test-installer                                  # la clé essayée seule de bout en bout, sans fenêtre (OCR)
CHARPENTIER_TOKEN=… scripts/flash-installer.sh          # écrire la dernière image publiée sur une clé (depuis le Mac)
scripts/flash-installer.sh --local                        # ou celle construite ici
scripts/nix.sh flake update charpentier                   # passer au dernier commit de l'app
scripts/nix.sh --clean                                    # rendre le disque
```

Le cache Nix prend 10 à 15 Go au plus fort (le store, ou sur le Mac le volume Docker `charpentier-nix`). `--clean` le vide ; la construction suivante le retélécharge. Seule la branche `main` de l'app, poussée sur GitHub, est prise : pour essayer une app pas encore poussée, `--override-input charpentier path:<chemin de l'app>` (par exemple `path:../charpentier-writer`, si elle est clonée à côté).

`scripts/try-installer.sh` démarre l'image dans une machine virtuelle à la façon du X250 (UEFI, disque SATA vierge, la clé en USB, 4 Go), avec KVM si `/dev/kvm` est là ; `--disk` redémarre ensuite sur le disque installé. Ne jamais démarrer la clé sur la machine qui construit : elle effacerait son disque.

`nix run .#test-installer` fait la même chose sans personne au clavier : il lit l'écran par OCR et tape par le moniteur de QEMU (clavier azerty, disque effacé, mot de passe, copie, clé retirée, redémarrage, un mot de passe faux refusé puis le bon, l'écran « Bienvenue » de l'app). Les captures de chaque étape restent dans `dist/test-installer`. C'est l'essai que la CI fait sur chaque pull request.

## Mises à jour du X250

Le X250 ne reçoit que des versions numérotées (D-31, phase 5.11 du plan de l'app) :

1. Une release `vX.Y.Z` de l'app envoie ici un `repository_dispatch` `app-release`. `.github/workflows/app-release.yml` fait viser ce tag à l'entrée `charpentier` du flake, relance `nix flake lock` et ouvre la pull request « app vX.Y.Z », réglée pour se fusionner seule.
2. `.github/workflows/ci.yml`, sur chaque pull request : les trois systèmes, la clé, puis `nix run .#test-installer` en machine virtuelle avec KVM. C'est le seul accord que main demande.
3. `.github/workflows/publish.yml`, quand la pull request arrive sur main : les trois systèmes copiés, signés, dans le cache du serveur de synchronisation (`https://charpentier.chatel.pm/nix-cache`), puis le pointeur `/api/updates/latest` (version, notes, systèmes), puis, à part, l'image de la clé (`/api/installer/<version>`, que `scripts/flash-installer.sh` télécharge). Cloudflare, devant le serveur, refuse toute requête de plus de 100 Mo : `scripts/publish.py` n'envoie que les chemins qui manquent au cache, et en morceaux de 95 Mio au plus (en-têtes `X-Part` et `X-Checksum-SHA256`) ; les NAR partent avant leurs `.narinfo`. Un changement du seul système part par une release de ce dépôt, taguée `X.Y.Z-N` (la version de l'app, puis celle du système) ; les autres commits sur main ne partent pas.

La version développement a son propre canal (D-42, phase 5.12 bis), jamais mêlé aux releases : `scripts/publish-dev.sh`, depuis le Yoga L13 ou par `.github/workflows/publish-dev.yml` (à la main seulement, `workflow_dispatch`, avec une autre app en option), copie dans le cache les deux systèmes développement (`x250-dev`, `x250-dev-qwerty`) puis écrit le pointeur `/api/updates/dev`. Son numéro : la version de l'app, puis `-dev.N`, N un de plus que la version déjà sur `/dev` quand elle a la même version d'app, sinon 1 (`0.2.0-dev.1`, `0.2.0-dev.2`…). Le serveur ne garde que la dernière version développement et efface du cache ce qu'elle seule utilisait, jamais rien d'une release. Une version d'écriture ne lit jamais `/dev`.

- Depuis le Yoga L13 : `CHARPENTIER_CACHE_TOKEN=… NIX_SIGNING_KEY_FILE=… scripts/publish-dev.sh [--app github:chatelp/charpentier/<commit>]`, avec le jeton du Yoga sur le serveur et la clé de signature, que Pierre fournit sans les afficher. Il faut `hosts/x250/dev-keys.pub` : sans clé, le X250 qui prendrait cette version perdrait SSH.
- Par la CI : les mêmes secrets que `publish.yml`, et les clés SSH dans la variable `X250_DEV_KEYS` du dépôt.

À régler une fois, dans GitHub, par Pierre :

- Secrets de ce dépôt :
  - `CHARPENTIER_OS_BOT_TOKEN` : un jeton fin limité à `chatelp/charpentier-os`, droits Contents et Pull requests en écriture. `GITHUB_TOKEN` ne suffit pas : ce qu'il pousse ou fusionne ne déclenche ni la CI de la pull request ni la publication.
  - `CHARPENTIER_CACHE_TOKEN` : le jeton de la CI sur le serveur (`docker compose exec server node main.js create-ci-token github-actions`).
  - `NIX_SIGNING_KEY` : la clé secrète de signature `charpentier-x250-1`, faite sur le Yoga L13 sans être affichée, posée là et gardée en secours dans le gestionnaire de mots de passe de Pierre. Sa clé publique est `hosts/x250/cache-key.pub`, que le X250 lira à la phase 5.12.
- Variable de ce dépôt (Settings › Secrets and variables › Actions › Variables) : `X250_DEV_KEYS`, les clés SSH publiques de la version développement, une par ligne (celles de `hosts/x250/dev-keys.pub`), pour `publish-dev.yml` seulement.
- Sur le serveur, pour publier depuis le Yoga L13 : un jeton à lui, `docker compose exec server node main.js create-ci-token yoga-l13`, fait par Pierre (le prodesk2021 est en production).
- Réglages : « Allow auto-merge » ; une règle sur main qui demande une pull request et le check « systèmes, clé et essai en VM », sans approbation.
- Dans l'app : le jeton `CHARPENTIER_OS_DISPATCH` qui envoie le `repository_dispatch`.

## Réglages du BIOS du X250

À faire une fois sur le X250 (F1 au démarrage), avant d'installer. Menus du BIOS N10ET63W (1.42), celui du X250 de Pierre :

- Startup → UEFI/Legacy Boot : « UEFI Only », et CSM Support : « No ». Le système ne démarre qu'en UEFI (systemd-boot).
- Security → Secure Boot : désactivé. Ni systemd-boot ni l'iPXE de l'installation par le réseau ne sont signés.
- Config → Keyboard/Mouse → « F1-F12 as Primary Function » : « Disabled ». La rangée du haut est alors le volume, la luminosité et le micro, que l'app lit ; F1 à F12 ne servent pas dans Charpentier OS. Fn+Échap bascule le même verrou à la main (le voyant de Fn allumé : F1 à F12 d'abord). Le système ne le voit pas : `thinkpad_acpi` n'en donne rien sur le X250.

## Installation par le réseau

Phase 5.9 ter (D-32) : le X250 démarre l'installateur par son câble Ethernet, sans clé (F12, puis la carte réseau). Le même installateur que la clé (`installer/default.nix`), en noyau, initrd (le système en mémoire, environ 1,5 Go compressé) et ligne de commande : `packages.netboot` (`installer/netboot.nix`), envoyé par `publish.yml` sur le serveur de synchro (`PUT /api/netboot/<version>/{bzImage,initrd,cmdline}`) avec l'image de la clé. Sur la maison, Pixiecore (profil `netboot` de l'app, éteint par défaut) répond en proxyDHCP sans remplacer la box et demande au serveur quoi démarrer : l'installateur pour la seule MAC du X250, rien aux autres. Sans clé, la fin de l'installation dit seulement « ⏎ redémarrer ».

- Préalables sur le X250 : « UEFI IPv4 Network Stack » activé dans le BIOS, Secure Boot désactivé (iPXE n'est pas signé).
- `scripts/try-netboot.sh` l'essaie sur le Yoga L13 **sans root et sans toucher à son réseau** : un espace de noms réseau à lui, un pont, dnsmasq dans le rôle de la box (dans son propre espace, sur le même pont), Pixiecore en mode API, un faux du serveur (`scripts/netboot-api.py`, le contrat de `apps/server/src/netboot.ts` de l'app) et une machine virtuelle qui démarre sur le réseau. `--other` : une autre MAC, qui ne reçoit rien. Essayé le 14 novembre 2026 : l'installateur en 55 s pour la MAC déclarée (noyau 12 Mio, initrd 1,46 Gio) ; « PXE-E16 No valid offer » pour l'autre, aucun fichier servi.

## Version développement du X250

Pour les essais depuis le Yoga L13 (phases 5.10 et 5.10 bis du plan) : le système d'écriture, plus un accès SSH **par clé seulement**, en tant qu'`auteur`, **depuis le réseau de la maison seulement** (port 22 ouvert aux seules adresses privées, IPv6 de lien local et ULA ; pas de Tailscale), et le mode d'essai de l'app (`CHARPENTIER_TEST_PORT=9222`, sur 127.0.0.1, joint par un tunnel SSH). Elle porte le marqueur `/etc/charpentier/variant` (`developpement`) et le tag `developpement` au menu de démarrage. Son service de mise à jour (5.12) lit le canal de développement, `/api/updates/dev`, et n'y prend que des systèmes développement ; celui d'une version d'écriture lit les releases seulement et la refuse toujours. La version d'écriture n'ouvre aucun port.

- Les clés admises : `hosts/x250/dev-keys.pub`, une par ligne (celle du Yoga L13), jamais commité (dans `.gitignore`) ni dans les sources du flake : il lui est donné comme entrée `dev-keys` (`--override-input dev-keys path:<fichier>`, ce que font `update-x250.sh`, `reinstall-x250.sh` et `publish-dev.sh` par `scripts/dev-keys.sh` ; `CHARPENTIER_DEV_KEYS=<fichier>` en donne un autre, la clé d'une machine virtuelle par exemple) ; leur commentaire (`utilisateur@machine`) n'entre pas dans le système, qui est publié sur le canal de développement. Sans elle, la version développement ne se construit pas.
- Une version sur le canal de développement (plus haut, « Mises à jour du X250 ») : le X250 la prend à sa vérification horaire, comme une release sur une version d'écriture (« mise à jour prête · ⊞R », « À propos », la ligne de l'écran du disque, le retour à la version précédente). Une mise à jour par `update-x250.sh` reste possible à côté, et la plus récente gagne (décision de Pierre, 18 novembre 2026) : le service ne prend une version de `/dev` que si elle a été publiée (`publishedAt` du pointeur) après la création du système le plus récent de la machine ; une publication plus ancienne qu'une mise à jour locale n'est jamais prise, une publication venue après redevient candidate.
- Première installation, à la main : `scripts/nix.sh --out dist/installer-dev build --override-input dev-keys "path:$PWD/hosts/x250/dev-keys.pub" .#installer-dev`, puis la clé (ou, pour la VM, `CHARPENTIER_VM=dist/vm-dev CHARPENTIER_IMAGES=dist/installer-dev scripts/try-installer.sh`).
- Mise à jour sans le toucher : `scripts/update-x250.sh <adresse>` (`--boot` pour le prochain démarrage seulement ; `--app <référence>` pour une autre app que celle du `flake.lock`, sans l'écrire : `--app github:chatelp/charpentier/<commit>` ou `--app path:../charpentier`). Le script vérifie le marqueur et choisit le système du clavier installé, pour ne jamais retirer l'accès SSH à la machine qu'il atteint. Un `switch` ne relance jamais la session lui-même (greetd n'est pas redémarré) : le script la relance quand elle a changé (la nouvelle app, sway), ce qui ferme l'app en cours.
- Réinstallation de zéro, à distance : `scripts/reinstall-x250.sh <adresse> <fichier du mot de passe du disque>`, par nixos-anywhere (redémarrage en mémoire, puis disque effacé et disposé comme par l'installateur, `hosts/x250/disko.nix`). Au redémarrage, le mot de passe du disque se tape sur le X250 (ou par le moniteur de QEMU).
- Les essais de l'app contre l'appareil (`apps/desktop/e2e/x250.device.ts` de l'app) : un tunnel `ssh -N -L 9222:127.0.0.1:9222 auteur@<adresse>`, le premier démarrage de l'app passé, la veille suspendue pendant les essais (`swaymsg '[app_id=".*"] inhibit_idle open'`), puis `CHARPENTIER_DEVICE=http://127.0.0.1:9222 pnpm --filter @charpentier/desktop test:device` (`CHARPENTIER_DEVICE_VM=1` en machine virtuelle, sans batterie).


- `flake.nix` : `nixosConfigurations.x250` et `x250-qwerty` (le clavier choisi à l'installation), `packages.installer` (l'ISO) ; la version développement `x250-dev` (`-qwerty`) et sa clé `packages.installer-dev`, publiées seulement sur le canal de développement, jamais avec les releases ; `checks.update-channels`, l'essai des deux canaux en machines virtuelles (`tests/update-channels.nix`, contre un faux serveur, `scripts/update-api.py` : `nix build .#checks.x86_64-linux.update-channels -L`, aussi dans la CI) ; `checks.update-generations`, le nettoyage du store et le retour d'un premier démarrage raté (`tests/update-generations.nix`, aussi dans la CI).
- `hosts/x250/` : le système (démarrage, chiffrement LUKS, session, réseau, son, impression, autorisations) et `vm.nix` pour l'essayer en machine virtuelle.
- `hosts/x250/dev.nix` : la version développement (ci-dessous) ; elle ne s'endort pas sur inactivité (le rabat, si), pour rester joignable par SSH.
- `hosts/x250/update/` : le service des mises à jour (phase 5.12) et la ligne « mise à jour » de l'écran du disque.
- `hosts/x250/plymouth/` : l'écran du mot de passe du disque (DESIGN §4.12 « Verrouillage »). Plymouth, dans l'initrd sous systemd, avec un thème `script` : systemd-cryptsetup lui demande le mot de passe, il dessine avec une vraie police (JetBrains Mono, licence OFL jointe) et lit le clavier de la console, donc la disposition choisie à l'installation. Sans lui, l'invite serait le texte anglais de systemd. `scripts/try-plymouth.sh` l'essaie dans une fenêtre, sans machine virtuelle.
- `installer/` : l'image de la clé et `install.sh`, l'installateur en mode texte.
- `scripts/` : `nix.sh` (construire), `try-installer.sh` (essayer la clé en machine virtuelle), `test-installer.py` (l'essayer seule, `nix run .#test-installer`), `try-plymouth.sh` (l'écran du mot de passe, dans une fenêtre), `publish.py` (envoyer au serveur, en morceaux), `publish-dev.sh` (la version développement sur son canal), `update-x250.sh` (mettre à jour un X250 en version développement par SSH) et `flash-installer.sh` (écrire la clé depuis le Mac, l'image publiée ou `--local`).
- `.github/workflows/` : `app-release.yml`, `ci.yml` et `publish.yml`, les mises à jour du X250 ; `publish-dev.yml`, la version développement, à la main.

## Ce que l'app attend du système

C'est le contrat entre les deux dépôts : un changement d'un côté demande souvent le changement correspondant de l'autre. Côté app, il est lu par le service `System` (`packages/platform-desktop/src/main/system`) et par `apps/desktop/src/main/index.ts`.

- **Lancement** : `charpentier --appliance`, sous sway (Wayland, `NIXOS_OZONE_WL=1`), relancé s'il s'arrête, tant que son sway répond (une session relancée ne laisse pas l'ancienne boucle derrière elle). L'app est alors tout l'écran, sans barre de menus.
- **Arrêt** : SIGTERM la fait quitter normalement ; ses programmes de longue durée (`nmcli monitor`, `udevadm monitor`, `swaymsg subscribe`, `swayidle`) sont lancés sous `setpriv --pdeathsig KILL` et meurent avec elle, même tuée (SIGKILL).
- **Verrou** : la session sway a un mode `locked`, où aucun raccourci de sway ne passe ; l'app y entre et en sort par `swaymsg mode locked|default`.
- **Clavier** : `/etc/charpentier/keyboard` contient `azerty` ou `qwerty` (le bépo a été retiré avant la v0.1.1 ; un X250 qui aurait encore `bepo` n'a plus de système publié pour lui).
- **Outils**, dans le `PATH` de la session, utilisables par l'utilisateur `auteur` sans mot de passe (règles polkit) : `nmcli`, `bluetoothctl`, `brightnessctl`, `wpctl`, `timedatectl`, `swaymsg`, `swayidle`, `wlsunset`, `lsblk`, `setpriv`, `udevadm`, `udisksctl`, `lpstat`, `lp`, `lspci`, `systemctl` (veille, redémarrage, arrêt).
- **Fichiers lus** : `/sys/class/power_supply`, `/sys/class/backlight`, `/sys/class/thermal`, `/sys/class/dmi/id/product_version`, `/sys/block`, `/proc/stat`, `/proc/cpuinfo`, `/proc/meminfo`, `/proc/uptime`.
- **Services** : NetworkManager, BlueZ, PipeWire, UPower, UDisks2, CUPS avec Avahi.
- **Mode d'essai** : dans la version développement seulement, l'app est lancée avec `CHARPENTIER_TEST_PORT=9222` ; jamais dans la version d'écriture.
- **Version** : `/etc/charpentier/variant` vaut `developpement` dans la version développement ; absent dans la version d'écriture.
- **Mises à jour** (phase 5.12, contrat 1, convenu avec l'app le 14 novembre 2026, la référence côté app est `docs/x250-update-contract.md` ; le service : `hosts/x250/update/`, essayé en machine virtuelle contre un faux serveur ; ses deux canaux, D-42, par `checks.update-channels`) :
  - Le compte : l'app écrit `~auteur/.config/charpentier/update-access.json` = `{"server", "token"}` (0600) à la connexion et au démarrage, et le retire à la déconnexion. Le service le lit en root sans le copier ; sans lui, rien n'est vérifié. Le jeton ne passe jamais sur une ligne de commande : un en-tête `Authorization: Bearer` pour le pointeur, un netrc (Basic) pour le cache, dans un dossier de root effacé à la fin.
  - Le pointeur : `GET <server>/api/updates/latest` sur une version d'écriture, `GET <server>/api/updates/dev` sur la version développement (D-42), jamais l'autre → `{version, notes, systems: {azerty, qwerty}, publishedAt}` (404 : rien de publié). `notes` est un texte, coupé aux sauts de ligne, sans lignes vides ni « - » de tête. Une version d'écriture n'accepte que `X.Y.Z` ou `X.Y.Z-N`, la version développement que `X.Y.Z-dev.N` ; tout autre numéro : `unreadable`. La version développement ne prend qu'une version publiée (`publishedAt`) après la date de sa génération la plus haute : le `publishedAt` de celle-ci quand le service l'a prise du pointeur (une publication venue pendant le téléchargement de la précédente reste donc plus récente qu'elle), sinon la date de sa création (une mise à jour par `update-x250.sh`, même avant le redémarrage) ; sinon, rien n'est pris, sans échec. Une publication sur `/dev` pendant que le X250 télécharge la précédente en efface les fichiers (le serveur ne garde que la dernière) : le service note `interrupted` ou `unreadable`, puis prend la nouvelle à la vérification suivante.
  - Le téléchargement : `nix-store --realise` du système du clavier installé, depuis `<server>/nix-cache` seulement, chaque chemin signé par la clé de `hosts/x250/cache-key.pub` (`require-sigs`) ; puis le système doit être du même clavier et de la même voie, un système d'écriture (pas de marqueur `variant`) sur une version d'écriture, un système développement (`variant` = `developpement`) sur la version développement, sinon `unreadable`. Il devient la génération du prochain démarrage (`switch-to-configuration boot`), jamais celle qui tourne.
  - Le registre `/var/lib/charpentier/update/` (0700) : `generations.json` (génération → version, notes, dates ; pour la première installation, la version du paquet de l'app) et `state.json` (`ready`, `setAside`, `lastCheck`, `failure`).
  - Fichier d'état `/run/charpentier/update.json`, écrit par le service (root), atomiquement (écrit à côté puis renommé), mode 0644, réécrit à chaque démarrage du service ; absent, l'app ne montre rien :
    `{ "contract": 1, "installed": {version, generation, installedAt, notes[], dataFormat}, "ready": {version, generation, publishedAt, receivedAt, notes[]} | null, "previous": {version, generation, dataFormat} | null, "setAside": {version, generation, dataFormat} | null, "lastCheck": ISO | null, "checking": bool, "failure": {version, at, reason} | null, "development": bool }`, `reason` parmi `signature`, `unreadable`, `disk-full`, `interrupted`, et `start` (ajouté le 20 novembre 2026 : la version n'a pas démarré, le X250 est revenu à la précédente, ci-dessous).
  - `version` : la version du système, `X.Y.Z` ou `X.Y.Z-N`, ou `X.Y.Z-dev.N` sur la version développement, que l'app affiche telle quelle sans la comparer ; `notes` : les lignes du pointeur lu ; `dataFormat` : `<app>/share/charpentier/data-format` du paquet de l'app de la génération (absent : 1).
  - `ready` : téléchargée, signature vérifiée, déjà génération par défaut du prochain démarrage. Le service ne redémarre jamais, sauf au premier démarrage raté d'une génération (ci-dessous).
  - Premier démarrage raté (relecture du 18 novembre 2026) : au premier démarrage d'une génération, `charpentier-update-watch.service` attend que l'app tourne (le processus `--appliance` d'`auteur`, depuis 30 s au moins), 5 minutes au plus, en tâche de fond. S'il ne la voit jamais (Sway ne démarre pas, l'app meurt sans cesse), il fait le geste « revenir » de l'app vers `previous` (la génération devient `setAside`), note `failure` = `{version, at, reason: "start"}` et redémarre le X250. Une génération n'est surveillée qu'une fois : venue à l'écran, ou renvoyée, plus jamais ; arrêtée avant le verdict (la touche d'alimentation tenue), elle l'est de nouveau au démarrage suivant. Sans génération précédente (la première installation), rien n'est fait.
  - Le disque nettoyé (même relecture) : chaque jour, `charpentier-update-clean.service` retire les générations dont personne n'a besoin, puis ce que plus rien n'utilise dans le store (`nix-store --gc`). Restent : celle qui tourne, `previous`, `ready`, `setAside`, celle du prochain démarrage et la plus haute (la date de la version développement). Le menu de démarrage est réécrit sans les autres, l'entrée de `ready` garde sa ligne `charpentier.maj`. Essayé en machine virtuelle : `checks.update-generations`.
  - `setAside` : la version quittée par « revenir » ; plus annoncée, sauf si une plus récente arrive.
  - `development` : `true` dans la version développement, qui suit le canal `/api/updates/dev` (avant D-42, le service n'y installait rien).
  - Commandes, pour `auteur`, sans mot de passe (polkit, `manage-units` limité à ces unités) : `systemctl start --no-block charpentier-update-check.service` (la même vérification que le minuteur horaire, réseau présent) ; `systemctl start charpentier-update-boot@<génération>.service`, qui n'accepte que la génération de `previous` ou de `setAside`, en fait celle du prochain démarrage, met à jour `setAside` puis le fichier et répond 0 (toute autre génération : code non nul, rien ne change). L'app lance ensuite `systemctl reboot`.
